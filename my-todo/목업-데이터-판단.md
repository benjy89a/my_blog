# 목업 데이터 필요 여부 판단: 나만의 투두리스트

## 결론
**목업 데이터가 필요하다.**

이번 구현 범위에는 백엔드(데이터 저장)가 없다. 그래서 앱을 처음 열었을 때 화면에 보여 줄 데이터가 하나도 없다. 미리 넣어 둔 목업 데이터가 있어야 목록 선택, 완료 정렬 같은 요구사항을 바로 확인할 수 있다.

## 판단 근거 (PRD의 화면·요구사항)

| PRD 항목 | 목업 데이터가 필요한 이유 |
|---|---|
| 핵심 화면: 왼쪽 목록 + 오른쪽 할 일 | 빈 화면으로는 두 영역이 함께 동작하는지 볼 수 없다 |
| R1 목록 전체 보기 | PRD에 "앱을 열면 목업 목록(공부, 업무, 개인)이 보인다"는 조건이 있다 |
| R2 목록 선택 | 목록마다 다른 할 일이 들어 있어야 "선택한 목록의 할 일만 보인다"는 조건을 확인할 수 있다 |
| R5 완료 체크 | 완료된 할 일과 미완료 할 일이 섞여 있어야 "완료 항목이 맨 아래로 내려간다"는 조건을 확인할 수 있다 |
| R7 이름 수정 | 고칠 수 있는 할 일이 미리 있어야 바로 시험해 볼 수 있다 |
| 이번 구현 범위 | 새로고침하면 처음 상태로 돌아가므로, 매번 같은 조건으로 다시 확인할 기준 데이터가 필요하다 |

## 확인할 내용

| 상황 | 목업 데이터에 담을 것 | 확인할 조건 |
|---|---|---|
| 기본 목록 | 목록 3개: 공부, 업무, 개인 | 왼쪽에 3개가 보이고 첫 번째 목록이 선택되어 있다 |
| 목록별 구분 | 목록마다 다른 할 일 2~3개 | 목록을 바꾸면 그 목록의 할 일만 보인다 |
| 완료 정렬 | 각 목록에 완료(`done: true`) 1개 이상 | 완료 항목은 취소선이 있고 맨 아래에 있다 |
| 긴 이름 | 아주 긴 이름의 할 일 1개 | 글자가 영역 밖으로 넘치지 않는다 |
| 빈 목록 | 할 일이 하나도 없는 상태 (할 일 배열을 `[]`로 바꿔서 확인) | 빈 화면이 깨지지 않고 안내 문구가 보인다 |

## 데이터 항목

목록과 할 일을 두 배열로 나눈다. 각 할 일에는 어느 목록에 속하는지(`listId`)를 적는다.

**목록 (lists)**

| 필드 | 자료형 | 설명 |
|---|---|---|
| `id` | 숫자 | 중복 없는 고유 번호 |
| `name` | 문자열 | 목록 이름 (예: "공부") |

**할 일 (todos)**

| 필드 | 자료형 | 설명 |
|---|---|---|
| `id` | 숫자 | 중복 없는 고유 번호 |
| `listId` | 숫자 | 속한 목록의 `id` |
| `title` | 문자열 | 할 일 이름 |
| `done` | 불리언 | 완료 여부 (`true` = 완료, `false` = 미완료) |

## 나중에 백엔드로 바꿀 때
- 목업 데이터는 `data/` 폴더의 JSON 파일 한 곳에만 둔다. 화면 컴포넌트 안에 데이터를 직접 적지 않는다.
- 나중에 서버(API)를 연결해도 **같은 필드 구조**로 받으면, 데이터를 가져오는 부분만 바꾸면 된다. 화면은 거의 그대로 쓸 수 있다.
- 알림 시간 같은 새 필드는 백엔드를 연결할 때 추가한다.
